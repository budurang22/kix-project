# TDD 적용 기록

> 상태: **시작 전**. 실제 개발 진행에 맞춰 채운다 (미리 결과를 적지 않는다).
> 이 문서는 TDD로 개발한 기능과 구현 후 테스트를 추가한 기능을 구분해서 기록한다.
> 규칙: `.claude/rules/testing.md`, 결정: `docs/decisions.md` DEC-023

## 1. 적용 목적과 범위

테스트 주도 개발 경험을 확보하고 핵심 비즈니스 로직의 안정성과 데이터 정합성을 검증하기 위해 **부분적으로** TDD를 적용한다. 프로젝트 전체에 강제하지 않는다.

| 구분 | 기능 | 테스트 종류 | 대응 시나리오 |
| --- | --- | --- | --- |
| **TDD 필수** | 상품 옵션 재고 차감 | 단위 + MySQL 통합 | T-06 |
| **TDD 필수** | 재고 부족, 잘못된 주문 수량 검증 | 단위 | T-08(재고 0), T-12(수량 0) |
| **TDD 필수** | 주문 금액 계산, 가격 스냅샷 | 단위 + MySQL 통합 | T-05 |
| **TDD 필수** | 주문 멱등성, 중복 주문 방지 | MySQL 통합 | T-02, T-02b, T-03 |
| **TDD 필수** | 동시 주문 시 재고 초과 판매 방지 | MySQL 통합 | T-01, T-02, T-06 |
| 일반 테스트 | 트랜잭션 롤백 | MySQL 통합 | T-04 |
| 일반 테스트 | 회원가입·로그인, 인증·인가 | MockMvc, 통합 | T-11 |
| 일반 테스트 | 상품 CRUD | MockMvc, `@DataJpaTest` | - |
| 일반 테스트 | 리뷰·좋아요 | 통합 | T-09, T-10 |
| 일반 테스트 | API 입력값 검증 | MockMvc | T-12 일부 |

- 동시성, 멱등성, 트랜잭션, DB 제약조건은 실제 MySQL(Docker Compose)에서 검증한다.
- 위 구분은 계획이다. 실제로 TDD 순서로 진행한 기능만 3장 기록에 "TDD"로 표시한다.

## 2. 진행 절차 (12단계)

1. 요구사항과 비즈니스 규칙 정의
2. 테스트 시나리오 작성
3. 실패하는 테스트 코드 예시 제공 (Claude)
4. 테스트 코드를 직접 작성하고 실행 (개발자)
5. RED 확인
6. 최소 구현 예시 제공 (Claude, RED 확인 후)
7. 직접 구현 (개발자)
8. GREEN 확인
9. 리팩터링 방향 설명
10. 직접 개선
11. 전체 테스트 재실행
12. 이 문서에 기록

RED는 의도한 이유로 단언이 실패한 상태다. 컴파일 오류만 나는 상태는 RED로 치지 않는다.
